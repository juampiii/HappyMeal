# Layers and Flows

## Domain Layer

`Happymeal.Domain` owns the business model. Put a rule here when it describes what a business object is allowed to be or do, independent of HTTP or the database.

What lives here:

- `Base/Entity`: identity only, a `Guid Id` with a private setter. The id is always passed in, never generated by the base class.
- `Base/AggregateRoot`: `Entity` that raises domain events (`AddDomainEvent`, `GetDomainEvents()`, `PullDomainEvents()`). Only aggregate roots raise events. Events are exposed through methods, so EF never maps them and Domain needs no `[NotMapped]`.
- `Base/IAuditable`: `CreatedOn`, `CreatedBy`, `ModifiedOn`, `ModifiedBy`, with private setters on the entity. Domain never sets them; the `AuditableInterceptor` in Infrastructure does (see [`runtime-and-integrations.md`](runtime-and-integrations.md)).
- `Base/DomainEvent`: `abstract record DomainEvent : IDomainEvent`. Every domain event derives from it.
- `Params/*`: input records for factories and update methods. Each one implements `IValidatable` (`Happymeal.Common.Validation`) and holds its own rules in `Validate()` (`RecipeParams`).
- `Events/*`: one file per domain event, a sealed record with primitive fields, named `<Entity><PastTenseVerb>DomainEvent` (`RecipeCreatedDomainEvent`, `RecipeUpdatedDomainEvent`, `RecipeDeletedDomainEvent`).

Domain has no third-party packages. It only references `Happymeal.Common`.

Entities expose intent through `static Create(...)` and methods such as `Update(...)` or `MarkAsDeleted()`. They normalize the input, call `Validate()` on the params, return the `Error` when it fails, and raise a domain event when the change is real. `Create` returns `Result<T>`; mutators return `Result`. Setters stay private. Length limits are `public const` on the entity, so the rules and the EF configuration share them.

```csharp
// RecipeParams.cs
public sealed record RecipeParams(string Name, string? Description) : IValidatable
{
    public IEnumerable<ValidationFailure> Validate()
    {
        if (string.IsNullOrWhiteSpace(Name))
        {
            yield return new ValidationFailure(nameof(Name), "Name is required.");
        }
        // ...
    }
}

// Recipe.cs
public static Result<Recipe> Create(Guid id, RecipeParams parameters)
{
    var normalized = Normalize(parameters);
    if (ValidateId(id).Concat(normalized.Validate()).ToValidationError() is { } error)
    {
        return error;
    }

    var recipe = new Recipe(Guid.CreateVersion7()) { Name = normalized.Name, Description = normalized.Description };
    recipe.AddDomainEvent(new RecipeCreatedDomainEvent(recipe.Id, recipe.Name));
    return Result.Success(recipe);
}
```

Rules:

- Validate the input before changing state, never the entity after. A failed `Update` must leave the entity untouched.
- `Validate()` returns every failure, not only the first one, so the client gets all field errors at once.
- `PropertyName` is the C# name (`nameof(Name)`). The API converts it to the JSON name.
- Expected invalid input returns an `Error`. Exceptions are only for programming errors (`ArgumentException`, `InvalidOperationException`). Throwing still costs microseconds per exception, so never use it for validation flow.

Chosen over Campus-BE and Catalog-BE: no FluentValidation, no `DomainResult`, no `DomainChangeRequestBase`. Chosen over eShop: `IValidatable` is inspired by `IValidatableObject` in `BasketItem`, but it is called by the factory itself, so an invalid entity cannot exist. Domain methods are synchronous, so they have no `Async` suffix.

## Application Layer

`Happymeal.Application` handles commands and queries. It defines contracts and coordinates Domain and Infrastructure abstractions. It does not use EF Core or HTTP directly.

What lives here:

- `Common/Messaging`: `ICommand`, `ICommand<TResponse>`, `IQuery<TResponse>`, `ICommandHandler<TCommand>`, `ICommandHandler<TCommand,TResponse>`, `IQueryHandler<TQuery,TResponse>`, `ISender` and its internal `Sender`.
- `Common/Interfaces`: `IUnitOfWork` and repository interfaces implemented by Infrastructure.
- `Features/<Feature>/`: `Commands/<Name>/` and `Queries/<Name>/` folders, each with a single `<Name>Feature.cs` containing the nested request record and its handler. Feature DTOs (`RecipeDto` with a static `From(entity)` mapper) sit at the feature root. Domain event handlers go in `DomainEventHandlers/`.
- `Configuration/ServiceExtensions.AddApplicationServices`: registers request handlers, `ISender` and the domain event handlers of this assembly.

### Commands, queries and handlers

Each use case has one `<UseCase>Feature.cs` file with a public static container and nested public request and handler types. Commands use `Command`, queries use `Query`, and both use `Handler`. Keep existing folders and namespaces; the Feature suffix avoids collisions with the namespace. The assembly scanner registers public nested handlers.

```csharp
// Request declarations; each file also contains its own nested Handler.
public static class CreateRecipeFeature
{
    public sealed record Command(Guid? Id, string Name, string? Description) : ICommand<RecipeDto>;
}

public static class DeleteRecipeFeature
{
    public sealed record Command(Guid Id) : ICommand; // no response value
}

public static class GetRecipeByIdFeature
{
    public sealed record Query(Guid Id) : IQuery<RecipeDto>;
}

public interface ICommandHandler<in TCommand> where TCommand : ICommand
{
    Task<Result> HandleAsync(TCommand command, CancellationToken cancellationToken = default);
}

public interface ICommandHandler<in TCommand, TResponse> where TCommand : ICommand<TResponse>
{
    Task<Result<TResponse>> HandleAsync(TCommand command, CancellationToken cancellationToken = default);
}

public interface IQueryHandler<in TQuery, TResponse> where TQuery : IQuery<TResponse>
{
    Task<Result<TResponse>> HandleAsync(TQuery query, CancellationToken cancellationToken = default);
}
```

- Commands change state. Queries only read. A query handler never calls `SaveEntitiesAsync`.
- Chosen over eShopOnContainers: queries have handlers (not an `OrderQueries`-style class with Dapper), so commands and queries share one dispatch path.
- `AddApplicationServices` scans the assembly and registers every closed handler interface. No manual registration.
- Callers use `ISender.SendAsync(request)`. It resolves the single handler for the request type (`IMediator.Send` in eShop). A missing handler throws `InvalidOperationException`: that is a wiring bug, not a business outcome.

### Result and Error

`Happymeal.Common.Results` has one result type for every layer, Domain included:

| Type | Used for |
|------|----------|
| `Result` | Operations without a value: entity mutators, `ICommand` handlers, domain event handlers, the dispatcher. |
| `Result<T>` | Operations with a value: entity factories, `ICommand<T>` and `IQuery<T>` handlers, the outbox serializer. |
| `Error(ErrorType Type, string Message)` | The failure. `ErrorType`: `Failure`, `Validation`, `BadRequest`, `NotFound`, `Conflict`. `Validation` errors also carry `ValidationErrors` (C# property path -> messages). |

`Happymeal.Common.Validation` has `IValidatable`, `ValidationFailure(PropertyName, Message)` and `ToValidationError()`, which returns an `Error` of type `Validation`, or `null` when there are no failures.

Build results with the factories and the implicit conversion from `Error`:

```csharp
return Error.NotFound($"Recipe {command.Id} was not found.");   // converts to Result / Result<T>
return createResult.Error!;                                    // pass a domain failure through
return Result.Success(RecipeDto.From(recipe));                 // Result<RecipeDto>
return Result.Success();                                       // Result
```

Read them with `IsSuccess`/`IsFailure`, `Error` and `Value`. `Value` throws on a failed result, so check `IsFailure` first. There is no "NoContent" outcome: a successful non-generic `Result` becomes `204` in the API.

### Handler shape

```csharp
public static class UpdateRecipeFeature
{
    public sealed record Command(Guid Id, string Name, string? Description) : ICommand<RecipeDto>;

    public sealed class Handler(IUnitOfWork unitOfWork) : ICommandHandler<Command, RecipeDto>
    {
        public async Task<Result<RecipeDto>> HandleAsync(Command command, CancellationToken cancellationToken = default)
        {
            var recipe = await unitOfWork.RecipeRepository.GetAsync(command.Id, cancellationToken);
            if (recipe is null)
            {
                return Error.NotFound($"Recipe {command.Id} was not found.");
            }

            var updateResult = recipe.Update(new RecipeParams(command.Name, command.Description));
            if (updateResult.IsFailure)
            {
                return updateResult.Error!;
            }

            await unitOfWork.SaveEntitiesAsync(cancellationToken);
            return Result.Success(RecipeDto.From(recipe));
        }
    }
}
```

Handlers use guard clauses, delegate invariants to Domain, return `Result` for expected outcomes and call `SaveEntitiesAsync` once.

## Infrastructure Layer

`Happymeal.Infrastructure` implements Application contracts:

- `Database/HappymealDbContext` (default schema `Happymeal`), `Database/Configurations/*Configuration.cs` (one per entity, applied by assembly scan), `Database/Migrations/`, `DesignTimeHappymealDbContext` for the EF CLI.
- `Repositories/`: one repository per aggregate plus `UnitOfWork`. Repositories and `UnitOfWork` are `internal sealed`.
- `Outbox/`: `OutboxMessage`, `OutboxSerializer`, `OutboxOptions`, `OutboxDispatcher`.
- `Configuration/ServiceExtensions.AddInfrastructure(configuration)`.

Repository rules (eShop style): `GetAsync` returns a tracked entity, so changes and events are seen by `SaveEntitiesAsync`. List queries (`GetAllAsync`) use `AsNoTracking()`. `Add` and `Delete` are synchronous and only change the tracker. Nothing calls `SaveChanges` except `UnitOfWork.SaveEntitiesAsync` and the outbox dispatcher.

## API Layer

`Happymeal.API` is the HTTP layer and composition root:

- `Program.cs` calls `AddApiServices`, `AddApplicationServices`, `AddInfrastructure`, migrates the database in Development, then `UseApiServices`.
- Controllers live in `Controllers/`, one per feature (`RecipesController`, route `api/recipes`). They take `ISender` in the primary constructor. Request bodies are API DTOs in `Dtos/` and are mapped to commands in the action.
- Action methods end in `Async`. MVC removes the suffix from action names by default, so an action used as a `CreatedAtAction` target needs `[ActionName(nameof(GetByIdAsync))]`.
- `Extensions/ControllerExtensions.ToActionResult(...)` translates results to HTTP (see [`validation-strategy.md`](validation-strategy.md)). `Result` -> `204`, `Result<T>` -> `200` or the `onSuccess` override (`CreatedAtAction` on create).

## Main HTTP Flow

```text
HTTP request
  -> Controller (body DTO -> command/query)
  -> ISender.SendAsync -> ICommandHandler / IQueryHandler .HandleAsync
  -> Domain entity (Create / Update / MarkAsDeleted) -> Result<T> / Result
  -> IUnitOfWork repositories -> SaveEntitiesAsync (entity + outbox rows, one transaction)
  -> Result / Result<T>
  -> ControllerExtensions.ToActionResult
  -> HTTP response (200/201/204 or ProblemDetails)
```

## Identifiers

The domain receives the id; it never generates it. `Recipe.Create(Guid id, ...)` rejects `Guid.Empty`. The command handler picks the source:

```csharp
var id = command.Id ?? Guid.CreateVersion7();
```

- A client may send its own id (`CreateRecipeRequestDto.Id`). This makes creation idempotent for retries and allows optimistic UI.
- When the id already exists, the handler returns `Error.Conflict` (409). When resources become per user, keep returning 409 for ids of other users, so the API does not reveal that they exist.
- The existence check and the insert are not atomic. Two concurrent requests with the same id can both pass the check; the second fails on the primary key (500). There is a `// TODO` in `CreateRecipeFeature.Handler`.
- Guid v7 is time ordered and PostgreSQL compares `uuid` byte by byte, so v7 keys do not fragment the index.

## Unit of Work and Domain Events (outbox)

Chosen over Catalog-BE and eShopOnContainers: events are not dispatched in-process before `SaveChanges`. They go through a transactional outbox, like Campus-BE.

`UnitOfWork.SaveEntitiesAsync`:

1. Pulls the pending events from every tracked `AggregateRoot` (added, modified or deleted) with `PullDomainEvents()`.
2. Serializes each event into an `OutboxMessage` (full type name + JSON payload + new correlation id) and adds the rows to `OutboxMessages`.
3. Calls `SaveChangesAsync` once. Entity changes and outbox rows commit together or not at all. Returns `true` when something was written.

`OutboxDispatcher` (a `BackgroundService`) delivers them later. See [`runtime-and-integrations.md`](runtime-and-integrations.md) for the polling, claiming and retry rules.

Design rules:

- A handler runs after `SaveEntitiesAsync` returns, in its own DI scope, outside the caller's transaction. The HTTP response does not wait for it.
- Delivery is at least once. A handler can run more than once for the same event, so it must be idempotent.
- Only events on entities the change tracker sees are staged. Load the entity with the tracked `GetAsync`.
- To delete an aggregate and publish an event, call the domain method that raises the event (`MarkAsDeleted`) before `Repository.Delete`.
- Renaming or moving a domain event type breaks pending outbox rows, because they store the full type name. Make sure the outbox is empty before such a change, or keep the old type.

## Domain Event Handlers

A handler implements `Happymeal.Common.DomainEvents.IDomainEventHandler<TDomainEvent>` and returns `Result`:

```csharp
public sealed class LogRecipeLifecycleDomainEventHandler(ILogger<LogRecipeLifecycleDomainEventHandler> logger) :
    IDomainEventHandler<RecipeCreatedDomainEvent>,
    IDomainEventHandler<RecipeUpdatedDomainEvent>,
    IDomainEventHandler<RecipeDeletedDomainEvent>
{
    public Task<Result> HandleAsync(RecipeCreatedDomainEvent domainEvent, Guid correlationId, CancellationToken cancellationToken = default) { ... }
}
```

- Name handlers after the reaction, eShop style: `<Reaction>When<Event>DomainEventHandler` for one event (for example `CreateShoppingListWhenRecipeCreatedDomainEventHandler`), or `<Reaction>DomainEventHandler` when one class reacts the same way to several events.
- Put handlers with application logic in `Features/<Feature>/DomainEventHandlers/`. A handler that only talks to an external system belongs in Infrastructure.
- `AddDomainEventHandlers(assembly)` registers every closed `IDomainEventHandler<>` and records it in `IDomainEventHandlerCatalog`. A class may handle several events.
- Keep handlers thin. If the reaction is real business work, send a command with `ISender` and return its `Result`.
- A failed `Result` or an exception makes the outbox retry the message, up to `MaxAttempts`, then dead-letter it.
- An event with no handlers is marked processed and skipped.
